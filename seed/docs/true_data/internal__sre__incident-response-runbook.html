Incident Response Runbook (Platform SRE)

Synthetic internal document for the ADV RAG demo. Owner: Platform SRE. Applies to every production and DR Kubernetes cluster.

1. Severity levels

  • P1 (critical): customer-facing outage or data loss on a production cluster. Response SLA: acknowledge within 5 minutes, incident commander assigned within 10 minutes, target MTTR under 60 minutes.
  • P2 (major): degraded service, failing canary, or a production alert that is not yet an outage. Acknowledge within 15 minutes, target MTTR under 4 hours.
  • P3 (minor): single-pod or non-production issue. Handle in business hours, target MTTR 2 days.
  • P4 (informational): tracking only.

2. First response: what to do first

  1. Acknowledge the page and open an incident channel named #inc-<date>-<cluster>.
  2. Check cluster health: kubectl get nodes, kubectl get pods -A --field-selector=status.phase!=Running.
  3. For an open P2 alert, first confirm the alert is real (check the Grafana panel linked in the alert), then identify the owning deployment from the alert's source pod and check its recent rollouts with kubectl rollout history deployment/<name>.
  4. If a rollout in the last 2 hours correlates with the alert, roll back first and investigate second: kubectl rollout undo deployment/<name>.
  5. Post a status update every 30 minutes for P1, every 60 minutes for P2.

3. Standard remediation procedures

CrashLoopBackOff

Run kubectl describe pod and kubectl logs --previous. Common causes are bad config (ConfigMap or Secret change), a failing liveness probe, or OOMKilled containers. Fix the config or raise the memory limit, then restart the rollout.

OOMKilled

Confirm the last state reason is OOMKilled. Compare usage against the memory limit and raise the limit or fix the leak. Never remove limits on shared clusters.

ImagePullBackOff / ErrImagePull

Verify the image tag exists in the registry and that the pull secret is attached to the service account.

Node NotReady / DiskPressure

Cordon the node, drain it with kubectl drain --ignore-daemonsets, and let the autoscaler replace it.

4. Reducing MTTR

  • Keep runbooks linked from every alert so the responder starts from the remediation step.
  • Prefer rollback over forward-fix during an active P1.
  • Pre-approve common remediations (rollback, scale-up, node drain) so no change ticket is needed mid-incident.
  • Track MTTR per cluster weekly; clusters with average MTTR above the SLA get a reliability review.

5. After the incident

Every P1 and P2 needs a blameless postmortem within 5 business days, with an RCA summary recorded in the incidents table and action items assigned to an owning team.
